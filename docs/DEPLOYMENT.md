# Deployment

How HeritOS reaches production, what the server holds, how schemas are imported, and how to release and roll back. The most important fact first: **pushing to `main` deploys to production.** Work on a branch, open a pull request, and never test against real client records. Local development and staging are in [LOCAL-STAGING.md](LOCAL-STAGING.md); backups and monitoring further down this file.

Confirm the actual account, project, branch and environment before any remote mutation.

## Environments and promotion path

| Environment | Where | Data | Status |
|---|---|---|---|
| Local staging | One laptop: `php -S` plus local MariaDB or MySQL | Synthetic records only | Built ([LOCAL-STAGING.md](LOCAL-STAGING.md)) |

## CI and deploy

- `.github/workflows/ci.yml`: on pull requests to `main` and pushes to `main`, Node 22, runs `npm ci`, `npm run lint`, `npm test` (Vitest), `npm run build`, `php -l` over `php-api`, `php php-api/tests/run.php` and the documentation check `node scripts/check-docs.mjs` ([docs/README.md](README.md#how-the-docs-stay-current)).
- `.github/workflows/deploy.yml`: on every push to `main`, Node 22, runs `npm ci`, `npm run lint`, `npm test`, the PHP syntax check and helper tests, then `npm run build`; any failure, including a failing frontend test, stops the job before upload. It then copies the PHP files listed in the workflow into `dist/`: the original **nine** (`_lib`, `api`, `auth`, `ai`, `products`, `customers`, `stats`, `tailoring`, `contact`) and, on the Phase 2 branch, **seven** more (`_domain`, `_jobs`, `today`, `enquiries`, `measurements`, `quotes`, `ledger`), which had no hand-managed server copy. The Phase 3 branch adds `_mail`, `_portal`, `appointments`, `booking`, `access`, `portal` and `messages`, again new with no server copy, so a hand-uploaded caller never arrives before its include. The Phase 4 branch adds `_cms`, `_media`, `cms`, `site` and `sitemap`, also new; the Phase 5 branch adds `_company`, `companies` and `company_jobs`; the build itself ships `uploads/.htaccess` (from `public/uploads/`) and the new `robots.txt`. It then FTP-uploads `dist/` to the document root with `SamKirkland/FTP-Deploy-Action`.
- The other **22** endpoints (account, ai_image, analytics, content, coupons, engage, export, inbox, loyalty, mail, marketing, orders, payments, referrals, reviews, settings, stock, store, suppliers, users, weather, whatsapp) reach the server only by hand upload through cPanel. Their live versions are Unknown (A02). Any change to one of them must be listed in the pull request as a manual upload.
- Also by hand, never by CI: `config.php`, `.htaccess` (SPA routing, `RewriteBase /`, source in `php-api/.htaccess`), SQL imports, and the command-line tools `retention.php` with `_retention.php` (K-18) and `release_check.php` with `_release.php` (A02). `npm run release:manifest` derives the `ci` list from the `cp` lines of `deploy.yml` and marks every other tracked `php-api/*.php` and `.htaccess` as `manual` ([Release procedure](#release-procedure)).
- Website images (Phase 4 branch) live in `uploads/site/` in the document root, written only by `cms.php` on the server. They are not in Git or `dist/`. The FTP action keeps `.ftp-deploy-sync-state.json` on the server and deletes only files listed there that have gone from `dist/` (Verified against the FTP-Deploy documentation, Context7 `/samkirkland/ftp-deploy`, 11 October 2026), so a deploy never deletes uploaded images; `deploy.yml` also lists `uploads/site/**` under the action's `exclude` (with the action's default excludes repeated, because setting `exclude` replaces them) so the sync never looks inside it. Never switch on `dangerous-clean-slate`. Back up `uploads/site/` with the database: the two belong together.
- Deploy repeats the checks inside its own job rather than waiting on the CI workflow, so the trigger stays a plain push to `main` (A14, PR #6). Upload order matters when `_lib.php` gains functions: CI uploads `_lib.php`, so hand-uploaded endpoints that call the new functions (for example `account.php` and `store.php` after PR #6) go up after the deploy finishes, never before. Branch protection on `main` is Unknown and must be checked on GitHub, not assumed.
- Watch the repository Actions tab after a merge; the site is usually live within one to two minutes.

Older notes said "deploys only push dist/" and an older php-api/README.md said no PHP is auto-deployed. Both were wrong: the files above are deployed by CI (A19, fixed).

## Server configuration

`config.php` lives only in the server document root, copied from `php-api/config.sample.php`. It is gitignored and never copied between machines. Settings it holds (names only):

- Database: `DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASS`. cPanel prefixes names (the sample uses `devgeereact_heritage_com`).
- Debug: `GK_DEBUG` (false in production).
- Tokens and throttling: `TOKEN_SECRET`, `TOKEN_TTL_DAYS`, `LOGIN_THROTTLE_WINDOW`, `LOGIN_MAX_PER_IP`, `LOGIN_MAX_PER_ACCOUNT`, `PIN_MAX_PER_IP`, `PIN_MAX_GLOBAL`.
- Staff password reset (`feat/staff-password-reset`): `RESET_TTL_MINUTES` (default 30, 5 to 240), `RESET_MAX_PER_IP` (5), `RESET_MAX_PER_ACCOUNT_IP` (3, one address from one IP) and `RESET_FAIL_MAX_PER_IP` (10) over `LOGIN_THROTTLE_WINDOW`; `RESET_MAX_PER_ACCOUNT` (10, one address from anywhere) over `RESET_ACCOUNT_WINDOW` (default 3600 seconds, K-26; before K-26 `RESET_MAX_PER_ACCOUNT` meant 3 per address over the login window, so remove it from the server `config.php` if it was set there); `RESET_MIN_MS` (default 600, 0 to 5000), the shortest time any reset request takes to answer (K-25); links use `SITE_URL` (default `CORS_ORIGIN`). The email goes through the Phase 3 mail settings (`SMTP_*`, or PHP `mail()` when `SMTP_HOST` is empty), so reset works only once outgoing email works.
- Customer throttling: `CUSTOMER_LOGIN_MAX_PER_IP` (default 10), `CUSTOMER_LOGIN_MAX_PER_PHONE` (default 5), `TRACK_MAX_PER_IP` (default 20), all over `LOGIN_THROTTLE_WINDOW`. 0 switches a check off.
- Staff session cookie: `STAFF_COOKIE_AUTH` (default off; unset means off). **Required at release (D-025):** switch it on once HTTPS is confirmed, as part of the release, not as an optional extra. On: staff sign-in puts the token in the HttpOnly `__Host-herit_staff` cookie (with `__Host-herit_csrf` beside it; the prefix needs HTTPS and no cookie Domain, so nothing extra to configure) and writes need the `X-Herit-CSRF` header (A15, [SECURITY.md](SECURITY.md#staff)). To switch on safely: (1) the deploy with the new `_lib.php` and `auth.php` has finished; (2) the matching `users.php` is hand-uploaded after it; (3) the site is on HTTPS (the cookie is Secure); (4) set `define('STAFF_COOKIE_AUTH', true);` in `config.php`; (5) sign out, sign in again, then check one email sign-in, one PIN sign-in, one save and sign-out in a browser. Staff already signed in keep their old token until they sign out. Rollback: set it back to false. Staff who signed in under the cookie then get "Session expired" until they sign out and in again; nothing else changes.
- CORS: `CORS_ORIGIN`, and `ALLOW_LOCALHOST_CORS` (default off). Switch it on only for an agreed session that points development at production, and off again afterwards (A15).
- Public appointment requests (Phase 3 branch): `BOOKING_SLOTS_MAX_PER_IP` (default 60) and `BOOKING_REQUEST_MAX_PER_IP` (default 5) per `BOOKING_THROTTLE_WINDOW` seconds (default 3600). 0 switches a check off.
- Customer access (Phase 3 branch): `ACCESS_START_MAX_PER_IP` (default 10), `ACCESS_START_MAX_PER_REF` (5) and `ACCESS_VERIFY_MAX_PER_IP` (20) per `ACCESS_THROTTLE_WINDOW` seconds (900); `ACCESS_INVITE_HOURS` (24); `SITE_URL` (base of invite links, defaults to `CORS_ORIGIN`). Codes are hashed with `TOKEN_SECRET`, which must be set; access answers 503 without it. `STAGING_ACCESS_CODE_LOG` exists only in the local staging config and is ignored unless the staging router is running; never set it in production.
- Customer references: `ALLOW_LEGACY_ORDER_CODE_LOOKUP` (default true when unset). While true, tracking and customer sign-in also accept the old sequential `ORD-` code as well as the random public reference. On the Phase 3 branch it also keeps the old phone plus order code portal login, its raw tokens and its measurement form working; false switches all of those off, leaving verified access (D-021). Set it to false once customers have their public references (A06). D-025: switch it off 30 days after release, which ends the old GET order lookup and the old phone plus order code login (K-14).
- AI: `OPENROUTER_KEY`, `OR_MODEL`, `OR_MODELS`, `OR_REFERER`, `OR_TITLE`, `IMAGE_PROVIDER`, `OR_IMAGE_MODEL`, `OPENAI_IMAGE_KEY`, `STABILITY_KEY`. The old project memory recorded `OR_MODEL` as `anthropic/claude-sonnet-4.6` on the server; the sample default differs. The live value is Unknown from the repo.
- Mail: `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`, `SMTP_FROM_NAME`, `IMAP_HOST`, `IMAP_PORT`, `IMAP_USER`, `IMAP_PASS`. The mail host recorded previously is premium152.web-hosting.com. Blank `SMTP_HOST` falls back to PHP `mail()`; blank `IMAP_HOST` disables the inbox.
- WhatsApp: `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_ID`, `WHATSAPP_VERIFY_TOKEN`, and `WA_APP_SECRET` (redesign branch, optional: the Meta App secret; when set, webhook posts without a valid `X-Hub-Signature-256` are refused, when blank they are accepted and a warning is logged). Blank token means wa.me fallback mode. The webhook is `/whatsapp.php?action=webhook`.
- Payments: `PAYMENT_PROVIDER`, `PAYSTACK_SECRET`, `PAYSTACK_PUBLIC`, `FLW_SECRET`, `FLW_PUBLIC`, `STRIPE_SECRET`, `STRIPE_CURRENCY`, `STRIPE_USD_RATE`.
- Promotions: `LOYALTY_RATE`, `REFERRAL_REWARD` (0 means off).
- Public shop and review writes (redesign branch, optional; per IP per hour): `CHECKOUT_MAX_PER_IP` (default 10), `WAITLIST_MAX_PER_IP` (10), `SAVE_CART_MAX_PER_IP` (60), `REVIEW_MAX_PER_IP` (5), `GIFT_CHECK_MAX_FAILS_PER_IP` (10 failed gift card checks).
- AI caps (redesign branch, optional; per staff member per day): `AI_MAX_PER_USER_DAY` (default 200), `AI_IMAGE_MAX_PER_USER_DAY` (50).
- Website (Phase 4 branch): `SITE_URL` (also the base of sitemap and JSON-LD URLs; default `https://heritclothing.com`), `PUBLIC_UPLOAD_DIR` (default `<doc root>/uploads/site`, created on the first upload if the folder is writable), `PUBLIC_UPLOAD_URL` (default `/uploads/site`), `MEDIA_MAX_MB` (default 8). PHP's own `upload_max_filesize` and `post_max_size` must be at least `MEDIA_MAX_MB` (cPanel > MultiPHP INI Editor); the live values are Unknown, and a lower limit makes larger uploads fail with 413.
- Link previews (`feat/link-previews`, K-06): `SPA_HEAD_INJECTION` (default false). To switch on: set it to true, then in the server `.htaccess` comment the `RewriteRule ^ index.html [L]` line and uncomment `RewriteRule ^ spa.php [L]` (both are in `php-api/.htaccess`, which also keeps `spa.php` answers indexable). Do it only after sharing a service link on WhatsApp shows the site-wide default instead of the service; to switch off, swap the two lines back. `spa.php` falls back to plain `index.html` on any error.
- `OPENWEATHER_API_KEY`, `OPENWEATHER_UNITS`: present in the sample but unused; weather.php calls Open-Meteo.

Frontend environment: `VITE_API_BASE` only, documented in `.env.example`; production builds ignore it.

### Retention job

`php-api/retention.php` (K-18) runs from the command line only; over HTTP it answers 404. It reads the `retention_*_days` settings ([API-SPEC.md](API-SPEC.md#data-retention-settings-keys-k-18)) and needs `_lib.php`, `_retention.php` and `config.php` beside it in the document root. `php retention.php` is a dry run that prints a count per category; `--apply` deletes in batches of 500 and writes one `retention_purge` audit entry per category straight after that category's deletes, so an error later in the run never leaves earlier deletions unaudited. A second run while one is in progress stops (`GET_LOCK`). It exits 1 on any error and 2 on an unknown option, so cron mail or the log shows a failure.

Cron line (cPanel > Advanced > Cron Jobs, once a day at 03:30 server time). Replace `CPANEL_USER` and check the PHP path cPanel shows (often `/usr/local/bin/php`). Check that `/usr/local/bin/php -v` (with the same path as the cron line) shows `(cli)`: a CGI binary (`cgi-fcgi`) is refused with a message on stderr and exit code 1, so use the command-line binary instead:

```
30 3 * * * /usr/local/bin/php /home/CPANEL_USER/public_html/retention.php --apply >> /home/CPANEL_USER/retention.log 2>&1
```

Run `php retention.php` once by hand (cPanel Terminal) before adding the line and read the counts. Locally, `HERITOS_STAGING=1 php php-api/retention.php` uses `config.local.php` and the `heritos_staging` database ([LOCAL-STAGING.md](LOCAL-STAGING.md#local-staging)); without that variable it loads `config.php`, as on the server.

## Database and schema files

- First install: import `php-api/schema.sql` in phpMyAdmin. It creates the foundation and module tables and seeds one `super_admin`, `dev@heritclothing.com`.
- Where the full `schema.sql` aborts on a stale legacy table, import `schema_modules.sql` instead; it creates only the later-module tables.
- Then apply `schema_phase2.sql` onwards in numeric order, up to `schema_phase22.sql` on the Phase 2 branch, `schema_phase25.sql` on the Phase 3 branch `schema_phase26.sql` on the Phase 4 branch `schema_phase27.sql` on the Phase 5 branch `schema_phase28.sql` on the redesign branch and `schema_phase29.sql` on `feat/staff-password-reset` and `schema_phase30.sql` (retention settings, K-18) on `feat/hardening-2026-10-18` and `schema_phase31.sql` (section usage counts, Phase 7) on `feat/phase7-review` and `schema_phase32.sql` (D-025 policy defaults: retention periods, quote validity, deposit wording; fills only empty settings) on `feat/ceo-decisions` (later phases alter tables created earlier). Local staging imports exactly this order without errors and replays 18 to 22 over seeded data (10 October 2026). Which phases the live database has is Unknown until the owner runs `release_check.php --db` ([Release procedure](#release-procedure), step 3): it maps each schema file to one marker table, column or settings key and reports PRESENT or ABSENT.
- `users.php`, `mail.php` and `inbox.php` need no new tables.
- Phase-specific imports and their order relative to the merge are under [Owner actions per pull request](#owner-actions-per-pull-request).
- `CREATE TABLE IF NOT EXISTS` does not upgrade existing columns, and re-running a file is not automatically safe. Record which versions are applied and their dependencies. Keep versioned SQL in `php-api/`.
- Seed password: set it straight after import. Generate a hash locally with `php -r 'echo password_hash("CHOOSE-A-STRONG-PASSWORD", PASSWORD_BCRYPT, ["cost" => 12]), PHP_EOL;'` (cost 12 matches `STAFF_HASH_COST` in `_lib.php`; a lower cost is upgraded at the first sign-in), then run `UPDATE users SET password_hash = '<hash>' WHERE email = 'dev@heritclothing.com';`. Never commit or share the real password.
- Smoke test: `https://heritclothing.com/api.php` returns a JSON array; `npm run release:smoke -- https://heritclothing.com` runs it with the other read-only checks.

Table and schema inventory: [DATA-MODEL.md](DATA-MODEL.md#table-inventory).

## Branches, worktrees and machines

- Pushing `main` deploys. Work on a feature branch, push the branch and open a pull request. Never push, merge or rebase `main` without explicit authority. Never force-push a shared branch.
- Start work with `git pull --ff-only`. One concern per commit; push each verified batch.
- Code moves between the Mac (owns env files and secrets) and the Ubuntu build machine only through GitHub. Env files, keys and sessions never move and are never committed.
- No extra worktrees by default; one isolated branch or worktree only when concurrency needs it. Before removing any branch or worktree, inspect dirty and ignored work, compare commits to the base and confirm nothing unique is lost.

## Release procedure

The release tools live in `scripts/release/` (A02, A20). None of them writes to the live database: `backup.sh` and `release_check.php` only read, `restore-check.sh` writes only to a scratch database, and `smoke.sh` sends GET and HEAD requests only. In the steps below, `DOCROOT` is the cPanel document root (the folder holding `config.php`) and `~` is the cPanel home folder, which is outside it. Copy `backup.sh` and `restore-check.sh` to `~/heritos-tools/` once (cPanel File Manager), never into the document root.

1. **Before anything else, back up.** In cPanel Terminal: `bash ~/heritos-tools/backup.sh --config DOCROOT/config.php`. It writes `heritos-<db>-<UTC time>.sql.gz`, a `.counts` file, the uploads archive and SHA-256 files to `~/heritos-backups` (it refuses a folder inside the document root) and keeps the newest 14 sets (`--keep N`). Download the new set to the Mac as the copy away from the host.
2. **Prove the backup restores** (monthly, and before any release with a schema import). Create an empty database in cPanel > MySQL Databases whose name contains `restore` (for example `PREFIX_restorecheck`), give the `config.php` user ALL PRIVILEGES on it, then `bash ~/heritos-tools/restore-check.sh --config DOCROOT/config.php --scratch PREFIX_restorecheck ~/heritos-backups/<newest>.sql.gz --uploads ~/heritos-backups/<newest>.uploads.tar.gz`. Every table must show MATCH and the result PASS; record the time it took. Then `--drop-only`, or delete the scratch database in cPanel if the user cannot drop it. A restore always goes into a new or empty database whose name differs from the source; the script refuses anything else.
3. **Record what is live before the change.** On the Mac, on the commit that is live now (`git switch main && git pull --ff-only` before the merge), `npm run release:manifest` writes `release-manifest.json` (gitignored). Upload it to `~` (never the document root), copy `php-api/release_check.php` and `php-api/_release.php` into the document root once, and run `php DOCROOT/release_check.php --manifest ~/release-manifest.json --db`. It prints MATCH, DIFFERENT or MISSING for every PHP file and `.htaccess` (each marked `ci` or `manual`), and with `--db` which schema files the database has. Download any DIFFERENT manual file before you replace it: that is the rollback copy.
4. Use backward-compatible schema changes; prepare maintenance or read-only handling if needed. Do the "Before merging" imports and uploads for the pull request ([Owner actions per pull request](#owner-actions-per-pull-request)).
5. Merge only after CI passes. The deploy job repeats lint, tests and build, then uploads `dist/` and the `ci` files.
6. **Hand uploads, after the deploy finishes.** Upload the "After the deploy" files for the pull request in the order given, never before the deploy.
7. **Check the files.** On the Mac, on the merged `main`, run `npm run release:manifest` again, upload the new manifest to `~` and run `php DOCROOT/release_check.php --manifest ~/release-manifest.json --db`. It must end "every manual file matches" (exit 0). A DIFFERENT `ci` file means the deploy has not finished or failed; `--strict` makes those fail too. `--ignore .htaccess` leaves out a server `.htaccess` you changed on purpose (for example link previews switched on).
8. **Smoke test.** On the Mac: `npm run release:smoke -- https://heritclothing.com`. It checks the app shell, robots, sitemap, the public site config, `api.php`, that `auth.php?action=me` refuses without a token, that the command-line tools, config, shared includes and manifest are not served, and the security headers, HTTPS redirect and `X-Robots-Tag`. It sends GET and HEAD only and exits 1 on any failure.
9. Run the checks in [qa/LAUNCH-CHECKLIST.md](../qa/LAUNCH-CHECKLIST.md#production-check) with designated test records.

Any failure in steps 7 to 9 is the rollback trigger.

## Rollback

- Frontend and the CI-deployed PHP files: revert the merge commit on a branch, open a pull request, merge after CI; the deploy redeploys the previous build. Then repeat steps 7 and 8 with a manifest made from the reverted commit.
- Manually uploaded endpoints and `.htaccess`: re-upload the copies downloaded in step 3, then run `release_check.php` with the step 3 manifest; every manual file must MATCH again.
- Schema: restore from the pre-release backup only when a backward-compatible fix is not possible. Restore into a scratch database first (`restore-check.sh`) to prove the dump, then import it over the live database in phpMyAdmin during a quiet period, after a fresh backup of the current state. Rows written since the backup are lost; say so to the owner before choosing this.
- Website images: extract the uploads archive from step 1 over `uploads/site/` (`tar -xzf <set>.uploads.tar.gz -C DOCROOT/uploads`).
- If a gate fails in production, disable the affected public action and keep a truthful enquiry channel rather than advertising working bookings or payments.

### Release tools on local staging

- `npm run release:manifest -- --out <file>` and `php php-api/release_check.php --manifest <file>` compare the working tree; `HERITOS_STAGING=1 php php-api/release_check.php --manifest <file> --db` reads the `heritos_staging` markers.
- `npm run release:smoke -- --api-only --no-headers http://127.0.0.1:8088` against `npm run staging:serve` (the router serves `php-api/` only and reads no `.htaccess`); `npm run release:smoke -- --site-only --no-headers http://127.0.0.1:<port>` against `npm run preview`.
- `bash scripts/release/backup.sh --config php-api/config.local.php --out <folder outside the repository>`, then `HERITOS_DB_ADMIN=mariadb bash scripts/release/restore-check.sh --config php-api/config.local.php --scratch heritos_restore_check --create --drop <dump>`. Only `heritos_restore_check` is ever created or dropped.

Decision (A02): the manifest is not uploaded by the deploy job and never placed in `dist/`. It holds no secrets, but at `/release-manifest.json` it would publish the name of every hand-uploaded endpoint and tool. It is deterministic for a commit, so the owner generates it on the Mac instead, and `php-api/.htaccess` denies it by name, together with `retention.php`, `release_check.php` and any `.sql`, `.sql.gz`, `.tar.gz` or `.tgz` file left in the document root by mistake. `deploy.yml` is unchanged.

## Troubleshooting

- **Site 404 or wrong content:** a Cloudflare record may be orange-cloud (set it to grey) or point at the wrong IP. Hard refresh or use a private window to rule out cache.
- **"Database connection failed":** wrong credentials in `config.php`, or the DB user lacks privileges.
- **Endpoint errors on GET:** the table it queries does not exist; import the right schema file.
- **Deploy fails:** open the Actions run. An `npm ci` failure usually means `package-lock.json` is out of step; an FTP auth failure means the three repository secrets do not match the FTP account.
- **HTTPS warning:** SSL is still issuing; run cPanel > SSL/TLS Status > Run AutoSSL.
- **A page says it could not load something, with a Retry button:** the API request failed (A17 and K-02 replaced the old upload instruction with this plain message). The browser console has the technical detail. Usual causes: the endpoint missing on the server (for Enquiries on the Phase 2 branch, `enquiries.php`), a table or column missing because a schema file was not imported, or an expired session.
